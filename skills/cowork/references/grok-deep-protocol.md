# grok 전용 심층 프로토콜 — 2-pass (CoT + ToT → 자기 비판 → 재분석)

> `scripts/cowork.sh` 의 `run_grok()` 이 이 파일의 마커 블록을 읽어 grok 프롬프트에 주입한다.
> claude·codex·kimi 에는 주입하지 않는다(그들은 단일 pass).

## 왜 grok 만 2-pass 인가 (실측 근거)

같은 질문에 각 AI 가 쓴 시간(2026-07-16 세 AI 시절 실측, atlas-missing-behavior · android-iap 2건 —
2026-07-18 kimi 합류, 237s 로 grok 과 codex 사이):

| AI | 소요 | 비고 |
|---|---|---|
| grok | **132s · 202s** | 압도적으로 빨리 끝내고 **놀고 있었다** |
| claude | 320s · 398s · 399s | |
| codex | 573s · 717s | 가장 오래 판다 |

`final-report.md` 종합은 **모든 AI 가 전부 끝나야** 시작된다. 즉 cowork 1회의 벽시계 시간은 **가장 느린
codex(~12분)** 가 결정하고, grok 은 그중 2~3분만 쓰고 **9분을 버린다**. 그 시간은 공짜다 — grok 을
더 깊이 파게 해도 cowork 전체는 1초도 느려지지 않는다.

그래서 grok 에게만 두 번 일을 시킨다:

- **Pass 1** — CoT(단계적 추론) + ToT(가설 분기·가지치기)로 깊게 판다 → `.grok-pass1.md` 에 저장
- **Pass 2** — 그 결과를 **적대적으로 자기 비판** 하고, 드러난 구멍을 코드로 메워 다시 쓴다 →
  `grok-cowork.md`(최종)

Pass 2 가 Pass 1 을 입력으로 받는 것이 핵심이다. 한 번의 호출에 "깊게 분석하고 스스로 비판하라"고
적어봐야 모델은 자기가 방금 쓴 글을 관대하게 본다. **결과를 파일로 확정한 뒤 새 세션에서 남의 글처럼
공격** 해야 진짜 비판이 나온다.

## 핵심 로직 (cowork.sh run_grok 이 하는 일)

```bash
# Pass 1 프롬프트 = 아바타 페르소나 + GROK-PASS1 지침 + 사용자 요청
#   → sandbox-exec(repo 쓰기 차단) grok --prompt-file .grok-pass1-prompt.md > .grok-pass1.md
# Pass 2 프롬프트 = 아바타 페르소나 + GROK-PASS2 지침 + 사용자 요청 + Pass 1 결과 전문
#   → sandbox-exec(repo 쓰기 차단) grok --prompt-file .grok-pass2-prompt.md > grok-cowork.md
#
# 실패 처리: Pass 1 실패 → 실패로 확정(종합에서 grok 제외).
#            Pass 2 실패 → Pass 1 결과를 최종으로 승격(fallback). 깊은 분석 1회를 버리지 않는다.
# 제한 시간: 각 pass 에 COWORK_TIMEOUT 을 따로 건다(합계 최대 2×).
```

두 pass 모두 **읽기 전용 강제는 동일** 하다(`sandbox-exec` 로 repo subpath 쓰기 차단 —
[readonly-enforcement.md](readonly-enforcement.md) 참조). grok 은 CLI 옵션이 전부 무력하므로 이
래핑을 두 pass 어디서도 벗기지 말 것.

## 🔬 grok 전용 지침 — Pass 1 / 2 (깊이 탐색)

**당신에게는 시간이 많다. 빨리 끝내지 말라.** 이 분석은 다른 일곱 AI(claude·codex·kimi·agy·
deepseek·minimax·qwen)와 동시에 돌아가고, 그들은 이 문제에 **5~15분** 을 쓴다. 종합은 여덟이 모두
끝나야 시작되므로, 당신이 2분 만에 끝내도 아무도 빨라지지 않는다 — 당신만 얕아질 뿐이다. **끝까지 파라.**

이것은 2단계 작업의 **1단계** 다. 지금 쓰는 보고서는 곧 당신 자신에게 적대적으로 비판당한 뒤
다시 쓰인다. 그러니 지금은 **넓고 깊게 탐색** 하는 데 집중하라.

### CoT — 단계적 추론 (생각을 건너뛰지 말 것)

결론으로 점프하지 말고 다음 순서를 **실제로** 밟아라:

1. **질문 분해** — 무엇을 묻는지, 답하려면 어떤 사실이 필요한지 목록으로 만든다.
2. **진입점 특정** — 그 사실이 있을 파일을 찾는다(grep/glob). 추측한 경로를 사실로 쓰지 말라.
3. **한 단계씩 추적** — 호출 흐름을 따라간다. 각 단계마다 **파일을 실제로 열어** 확인한다.
   "아마 이럴 것이다" 로 다음 단계로 넘어가지 말라.
4. **경계 확인** — 이 문제가 어느 영역에 속하는가(어느 계층·어느 단계·누구의 결정 권한인지).
   어느 쪽이 권위(authoritative)인지가 결론을 바꾼다. 작업공간의 시스템 프롬프트(`.cowork/cowork-prompt.md`)와
   지침 문서가 그 경계를 정의한다.
5. **반대 증거 찾기** — 내 결론이 틀렸다면 어디에 흔적이 남는가? 그곳을 열어본다.

### ToT — 가설 분기와 가지치기 (하나만 보고 확신하지 말 것)

가장 그럴듯한 설명 하나에 매달리는 것이 이 작업의 가장 흔한 실패다. 반드시:

1. **가설을 최소 3개** 세운다. 서로 다른 층위에서(예: 대상 자료 자체 / 그것을 다루는 규칙·로직 /
   설정·환경 / 순서·타이밍 / 사람의 사용 방식).
2. **각 가설마다 자료로 검증** 한다 — 지지 증거와 반증 증거를 각각 찾는다.
3. **가지치기** — 반증된 가설은 버리되 **버린 이유를 기록** 한다(§0 에 남긴다). 나중에 그게 값지다.
4. 살아남은 가설이 2개 이상이면 **둘 다 남긴다.** 억지로 하나로 좁히지 말라 — 어느 쪽인지 가르는
   결정적 증거가 무엇인지를 §6 에 적는다.

### 최소 기준 (못 채우면 아직 덜 판 것이다)

- **파일을 12개 이상 실제로 열어라**(grep 히트만 세지 말고 내용을 읽어라). 작업공간에 파일이 그보다
  적으면 있는 것을 전부 열어라.
- **근거 10개 이상**, 전부 `파일:줄`(또는 출처) + 실제로 확인한 내용.
- **가설 3개 이상**을 세우고 각각 검증하라.
- 지침 문서(`.cowork/cowork-prompt.md`·`CLAUDE.md`·`README.md` 등)만 읽고 끝내지 말라 — **실제 자료가 진실**
  이다. 문서와 자료가 다르면 그 자체가 중요한 발견이다(§4 에 적어라).

### 출력 형식 (Pass 1)

아바타 지침의 **6개 섹션을 그대로** 쓰되, 맨 앞에 §0 을 하나 더 붙인다:

```
## 0. 탐색 로그 (ToT)

- 세운 가설: (1) … (2) … (3) …
- 검증: 가설 1 → `파일:줄` 로 확인 → 지지/반증
- 가지치기: 가설 2 는 `파일:줄` 때문에 버림 (이유)
- 열어본 파일: (경로 나열)
```

그 뒤에 `## 1. 결론 요약` ~ `## 6. 불확실 · 미확인` 을 아바타 지침대로 쓴다.

## ⚔️ grok 전용 지침 — Pass 2 / 2 (적대적 자기 비판 → 재분석)

아래 **"1차 분석 결과"** 는 방금 당신이 같은 질문에 대해 작성한 보고서다. 이제 당신의 임무는
그것을 **적대적으로 무너뜨리고, 살아남은 것만으로 더 나은 보고서를 다시 쓰는 것** 이다.

**자기 글이라고 봐주지 말라.** 남이 쓴 허술한 보고서를 리뷰한다고 생각하라. 시간은 충분하다 —
다른 AI 들이 아직 돌고 있다.

### 1) 먼저 공격하라 (이 단계를 생략하지 말 것)

1차 보고서의 **모든 주장** 에 대해 따진다:

- **근거가 실재하는가?** 인용된 `파일:줄` 을 **직접 다시 열어라.** 파일이 없거나, 줄 번호가 엉뚱하거나,
  내용이 주장과 다르면 그 주장은 **삭제** 한다. (AI 는 그럴듯한 경로를 지어낸다 — 당신도 예외가 아니다)
- **근거가 결론을 지지하는가?** 자료가 존재한다고 해서 그것이 그 결론을 뜻하지는 않는다. 논리 비약을
  찾아라.
- **반대 증거를 무시했는가?** 결론과 어긋나는 자료가 어딘가 있을 것이다. 찾아서 열어라.
- **놓친 가설이 있는가?** 1차에서 세우지 않은 4번째 설명은 없는가? 특히 1차가 한 가설에만 매달렸다면
  거의 확실히 있다.
- **경계를 틀렸는가?** 한쪽 영역의 문제라고 했는데 실은 다른 쪽이 권위인가? 이 판단은 자주
  뒤집히고, 뒤집히면 권고 전체가 무의미해진다.
- **이 프로젝트의 실제 제약을 어겼는가?** 시스템 프롬프트(`.cowork/cowork-prompt.md`)와 자료에서 읽어낸
  제약(대상 사용자·품질 기준·분량·기한·호환성·안전 규칙·검수 절차 등)을 무시한 권고는 실행 불가능한
  이상론이다. 특히 시스템 프롬프트에 명시된 금지사항을 어긴 권고는 그 자체로 실격이다.

### 2) 구멍을 자료로 메워라

공격으로 드러난 빈틈은 **추측으로 메우지 말고 파일을 더 열어라.** 1차에서 안 본 파일을 최소 몇 개는
새로 열게 된다. 그러지 않았다면 공격이 무른 것이다 — 다시 공격하라.

### 3) 다시 써라 (복붙 금지)

최종 보고서는 1차보다 **명백히 나아야** 한다:

- 반증된 주장은 **뺀다**(고쳐 쓰지 말고 뺀다).
- 살아남은 주장은 **더 강한 근거** 로 뒷받침한다.
- 새로 발견한 것을 넣는다.
- 1차와 결론이 **바뀌었다면 바뀐 대로** 쓴다. 1차를 방어하려 들지 말라 — 틀린 결론을 지키는 것이
  이 작업의 최악의 실패다.

1차를 그대로 옮겨 적기만 한 보고서는 **실패** 다. 비판할 게 정말 없었다면, 그건 비판을 안 한 것이다.

### 출력 형식 (Pass 2 — 이것이 최종 산출물이다)

아바타 지침의 **6개 섹션을 그대로** 쓴다(`## 1. 결론 요약` ~ `## 6. 불확실 · 미확인`).
§0 탐색 로그는 **넣지 않는다.** 대신 맨 뒤에 §7 을 붙인다:

```
## 7. 자기 비판으로 바로잡은 것

- ❌ 철회: (1차의 주장) — `파일:줄` 을 다시 여니 (실제 내용). 근거 없음.
- 🔁 수정: (1차 주장) → (바뀐 내용). 이유: `파일:줄`
- ➕ 추가: (1차가 놓친 발견) — `파일:줄`
- (없으면 "없음" 이라고 쓰되, 정말 없는지 다시 의심하라)
```

§7 은 종합(`final-report.md`) 단계에서 특히 값지다 — 다른 AI 가 그대로 믿었을 주장을 당신이 스스로
무너뜨린 기록이기 때문이다. **솔직하게 쓰라.** 틀렸던 것을 숨기면 그 오류가 최종 결론까지 올라간다.
